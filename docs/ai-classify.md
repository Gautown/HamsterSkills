# AI 判定（第二步）：分类 + 质量审查

规则层（[classify.md](./classify.md)）对低置信条目容易判错，这一层用 LLM 兜底；
同时把**质量审查**（keep / drop）合并进同一次调用——一次判定、两用输出，
不额外增加请求量。

- **分类**：装载 loader 的分类兜底（内容未变零成本）
- **质量审查**：判定为 `drop` 的技能由 loader 在构建时**硬删除**
  （不产页、不进索引、不进清单），口径与回滚见下方「质量审查」一节

## 架构

```
astro build ── loader 聚合远端技能（技能级门槛 SK1-SK4 之后）
      ↓
.cache/skills-remote/_manifest.json   技能清单：{id, sha, description, repo}
      ↓
scripts/ai-classify.mjs         调用 LLM（分类 + 质量双输出）
      ↓                         输入 = 名称 + 描述 + 正文摘录（仓库语料缓存按 sha 取）
.cache/ai-classify.json         记忆库：{ "<skillId>": { sha, category, quality, why, p, at, tokens } }
      ↓                          （由 .gitignore 忽略，但 Actions 缓存会保留）
astro build ── loader 读取记忆库：分类优先于规则层；quality=drop 的技能被硬删除
```

**记忆库是这一层的核心设计。** 站点页面由 `astro build` 通过 loader 产出，分类发生在构建期的 `mapSkillData` 里。
所以结果必须落在 loader 构建时就会读的文件里——落到别处（曾经的 `data/skills.json`）站点根本看不到。
好处是**无需改动站点任何代码**，一次 AI 分类，构建期直接生效。

### 输入为什么是「技能清单」而不是另行爬取的语料

清单由 loader 在**所有去重与上限都生效之后**写出，因此 `npm run ai-classify` 读到的
就是站点真实使用的技能集合：被 id 去重挤掉的、单仓/总量上限截断掉的、拉取失败的，都不在里面。

这带来两个直接好处：

- **不会白花钱** —— 脚本拿到什么就判什么，不存在「判了但站点用不到」的条目
- **脚本无需复刻任何规则** —— id 推导、仓库顺序、截断上限全部留在 loader 一处

> ⚠️ 清单里的 `id` 与记忆库的键是同一套推导（`src/lib/skill-id.mjs`）。
> 若在两处各写一份 id 推导，一旦出现细微差异，记忆库会**静默错位**：
> AI 花的钱记到用不上的键上，构建时查不到，只能退回规则层，且没有任何报错。
> 所以这个模块被两个消费方共用，不允许复制。

### 记忆化为什么用「skill id + 内容 sha + prompt 版本」

- 内容没变（sha 相同）→ 直接复用历史结果，**零 token**
- 上游改了 `SKILL.md`（sha 变化）→ 视为无缓存，重新判定
- **判定口径升级**（`AI_PROMPT_VERSION` 递增）→ 全部旧条目视为
  「未完成」自动进入回填；loader 侧也只认当前版本的判定结果。
  没有版本号，改了口径的判定永远不生效——这正是它存在的意义。

这让成本只随**新增和变更**增长，而不是随总量增长。

## 质量审查（第四级判定）

`ai-classify` 的每次调用同时输出 `q: keep | drop`（`why` 为 drop 的短证据）。
drop 的判定在 loader 提交技能时硬删除：不产页、不进 `skills-index.json`、
不进技能清单（AI 分类不再为它花钱）。

**判定口径（激进档，2026-10 用户选定）**，属于以下任一类判 drop：

- 不是真实可用的技能：模板、占位符、测试夹具、示例骨架、目录索引
- 空洞无实质内容：只有标题/口号，无可执行信息
- 纯营销或引流：像仓库宣传而不是技能说明
- 过时或未完成：明确废弃、TODO 占坑、内容残缺
- 质量平庸：表述混乱、无法照着执行、与通用常识重复无增量价值

拿不准时模型应选 keep（证据必须来自材料本身）。判定材料 =
名称 + 描述（前 200 字符）+ 正文摘录（前 260 字符，从仓库语料缓存按 sha 取，
缓存缺失时退化为仅描述）。

**三道放行阀（宁漏勿杀）**：

1. `SKILLS_AI_SCREEN=0` → loader 不拦截任何判定（影子模式）
2. 记忆库缺失 / sha 不匹配 / prompt 版本不匹配 → 视为未判定，放行
3. 只在规则门槛（SK1-SK4）之后生效——规则已删的不再花 AI 的钱

**回滚**：drop 只影响构建产物的收录，语料缓存与记忆库都保留。
关开关或调整口径（递增版本）重跑即可让内容回来。判定记录进
`_skill-gate.jsonl`（code=`AI1`）与 `npm run audit` 的 `=== skill gate ===` 一节。

## 用法

清单由构建写出，所以**必须先 build 再 classify**：

```bash
npm run build              # loader 在构建结束时写出技能清单
npm run ai-classify        # 处理清单里所有未记忆化的条目
npm run ai-classify:dry    # 只统计将发起多少请求，不调用
npm run ai-classify:status # 查看记忆库统计与分类分布
node scripts/ai-classify.mjs --limit 50            # 本次最多处理 50 条
node scripts/ai-classify.mjs --concurrency 5       # 提高并发
```

未配置 `AI_API_KEY` 时脚本直接跳过并返回，规则层分类照常生效。
清单不存在时同样跳过并提示先运行 `npm run build`。

## 环境变量

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `AI_API_KEY` | 空 | 必填才能运行；未配置则跳过 |
| `AI_API_BASE` | `https://api.agnes-ai.cn/v1` | OpenAI 兼容端点 |
| `AI_MODEL` | `agnes-3.0-flash` | 可选 `agnes-2.5-flash/pro` |
| `SKILLS_AI_SCREEN` | 开 | loader 侧开关，设 `0` 关闭质量硬删除（影子模式） |

## 实测得出的三个关键参数

这些取值不是猜的，是对目标接口实测后确定的：

| 参数 | 取值 | 原因 |
| --- | --- | --- |
| **不传 `response_format`** | — | 该模型在 `json_object` 模式下会忽略「输出数组」要求，只返回单个对象，导致 20 条请求只解析出 1 条。不传时 20/20 正常 |
| `max_tokens` | 2400 | 双输出（分类+质量+理由）后 20 条实测需要更多；1600 会偶发截断，截断直接判整批失败（拆单条重试） |
| `temperature` | 0 | 保证同样输入得到同样输出，判定可复现 |
| 批量 | 20 条/请求 | 实测 20 条 100% 合法，40 条时单请求延迟波动明显变大 |
| 并发 | 3 | 实测 5 并发时出现单请求 24s 的长尾 |

## 失败降级

```
批量请求失败 → 拆成单条重试（最多两轮）
单条仍失败  → 跳过该条，保留规则层结果（该条下次运行继续）
全部失败    → exit 1 → 流水线失败（部署被拦下；失败必须可见，
              不能让站点静默发布一轮「没有 AI 判定」的内容）
```

未配置密钥时脚本直接跳过（exit 0），站点照常构建、退回规则层分类。

## 成本

| 指标 | 数值 |
| --- | --- |
| 平均成本 | 分类约 50 tokens/条；双输出 + 正文摘录后约 120-200 tokens/条 |
| 批次成功率 | 20 条/批实测稳定；双输出的解析校验（category + q 双合法）见 parseResultMap |
| 全量回填（~4,800 条，含正文摘录与质量判定） | 约 240 请求 / 并发 3 约 30-40 分钟（一次性） |
| 日常运行（记忆库已建立且无口径变更） | **0 请求** |
| 内容变更的条目 | 按变更量计费，约 20 条/天 |

口径升级（`AI_PROMPT_VERSION` 递增）会触发一次全量回填——这是设计行为：
改了判定标准，旧判定就必须重来，否则新旧口径混杂无法解释站内内容。

## 速率限制处理

服务商对免费 key 的速率限制很紧（实测密集调用会返回 429）。批量请求撞上限制时，
**不能**沿用「拆成单条重试」的兜底 —— 一个 20 条的批次会变成 20 个请求，
在限流期间把请求量放大 20 倍，结果是整轮回填大面积失败。

实际策略（`src/lib/rate-limit.mjs`）：

1. 429 单独识别为 `RateLimitError`，与普通错误区分
2. 指数退避重试**同一个批次**：5s → 10s → 20s → 40s → 60s 封顶，
   服务端给了 `Retry-After` 则以服务端为准
3. 退避写入**全局节流器**，所有并发 worker 一起冷却 —— 否则每个 worker
   各自退避，总并发并没有真的降下来
4. 退避用尽仍被限流：放弃该批并计入失败，**不降级单条**。
   这些条目下次运行会继续处理（记忆库按 id + sha，未成功的不会留下记录）

非 429 的错误（解析失败等）仍走「拆单条重试」，因为那种情况下减小单次
请求量确实有帮助。

```bash
node scripts/ai-classify.mjs --rate-retries 8   # 加大限流重试次数（默认 5）
```

## CI

`.github/workflows/refresh.yml` 中，构建要跑两次：

```yaml
- name: 构建（写入技能清单）
  run: npm run build

- name: AI 分类
  run: npm run ai-classify | tee ai-output.txt

- name: 构建（应用 AI 分类）
  run: npm run build
```

**为什么构建两次**：记忆库是 loader 在构建期读取的，不重新构建就用不上刚写入的结果。
只构建一次的话，AI 分类要等第二天才上线。第二次构建时语料缓存已就位，
未变更的仓库走 `unchanged` 分支、**0 次网络请求**，只多花页面渲染时间，不多花 GitHub API 配额。

脚本自身的失败降级（见上）保证 AI 不可用时不会中断整条链路，最差情况退回规则层分类。

记忆库文件已加入 Actions 缓存的 path 列表，因此**每天只有真正的新增/变更条目会产生费用**。

### Secrets 配置

| 名称 | 类型 | 必需 |
| --- | --- | --- |
| `AI_API_KEY` | Secret | 是（缺失则跳过 AI，用规则层分类） |
| `AI_API_BASE` | Variable | 否，默认官方地址 |
| `AI_MODEL` | Variable | 否，默认 `agnes-3.0-flash` |
